Speculative product direction — whole app, not shipped

Where notchtap could go next, if this direction is picked up.

This is a roadmap deck, not a commitment and not an implementation spec — nothing rendered below exists in the real app. It extends prototypes/future-proposal.html, which redesigns exactly one corner (Settings → Agents, an adapter "doctor" ladder inspired by Handy). This file asks two broader questions: where else in notchtap does Handy's per-unit status clarity apply, and, on a mostly unrelated axis, how could notchtap's own v7 Agent-adapter pipeline get faster and feel more alive — using how snappy a fast local model feels as a directional target, not a technical parallel.

01Recap, not re-research

What Handy gets right (condensed from the verified log)

Every fact below is copied from future-proposal.html's own research log (WebFetch against github.com/cjpais/Handy and handy.computer, 2026-07-31) — this section does not re-fetch or add anything new. Handy is a local speech-to-text app on the same stack family as notchtap: Tauri, React/TypeScript/Tailwind frontend, Rust backend.

Confirmed — condensed from future-proposal.html
Per-model status Settings → Models shows each speech model (Whisper Small/Medium/Turbo/Large, Parakeet V2/V3/Unified EN 0.6B) as its own row: downloaded, or available to download. No blended "models: partial" chip — one unambiguous state per unit.
Speed as a fact Parakeet V3 (478MB, marked "recommended") claims ~5x real-time speed on mid-range hardware — speed is communicated as a plain, comparable number attached to the model row, not a vague "fast" label.
Two modes, visible Push-to-talk (hold) and toggle (press to start/stop), both configurable and both named plainly in the UI — not hidden behind one blended "recording" setting.
Offline-friendly A model file dropped into the app-data models directory is auto-discovered — no forced network round trip to make local state legible.
"One tool, one job. Transcribe what you say and put it into a text box."

The pattern worth generalizing is narrower than "copy Handy's UI": it's specifically one row per unit, one unambiguous status per row, no collapsing into a single blended signal — and, for §03 below, communicating speed as a concrete number/feeling rather than an adjective.

02Whole-app, not just Agents

Per-unit status clarity already shipped once — generalize it

Before proposing anything new: notchtap already has one shipped surface built exactly this way. It's worth naming as this deck's own precedent, not just Handy's.

✓

The overlay's StatusDots already does this

src/components/StatusDots.tsx (read in full) gives Football/News/Weather three independently-legible states — enabled (filled dot, glow), disabled (hollow square), and status unavailable (hollow circle, dimmer) — a real three-state shape encoding, plus a truthful aria-label per dot, plus a SEPARATE pause glyph so "the engine is paused" and "this source is off" stay two different, non-conflated facts. This is exactly Handy's instinct, already live, years before this deck. enabled · disabled · unavailable — shape-coded, not just colour-coded

Three surfaces don't yet get this treatment. None of the three below is invented from nothing — each is a real screen this deck read directly, with a real, specific gap.

Proposed — Connectors & Keys

ConnectorsSection.tsx today has exactly one row (OpenRouter API key) with a single MetaChip reading unset / a masked-suffix "set" state. Honest gap: with one row, "per-unit clarity" is trivially true today — the risk is a SECOND connector landing later without a deliberate shape for "N keys, some set, some not."

OpenRouter API key set ····a91f
(future) Weather provider key unset

Proposal: reserve the existing MetaChip active convention as the STANDING shape for every future secret row, and add a section-level rollup chip ("1/2 keys set") once a second key exists — the same "aggregate + per-unit" pairing §03's batching idea reuses below.

Proposed — History

HistorySection.tsx renders a flat, scannable list of past events with a per-row origin colour dot (historyOriginColor) — real and good, but there is no AGGREGATE view: no "how healthy has each source been recently" summary above the list, the thing a per-unit status row is usually for.

Agent 14 events · last 2m ago
Weather 3 events · last 40m ago
News 0 events today quiet

Proposal: a small per-origin summary strip above the existing list — count + recency per source — using data get_history already returns; no new backend surface, a frontend aggregation only.

03The pipeline itself

Making the Agent pipeline feel faster and more alive

A different axis from §02: not how status is DISPLAYED, but how quickly and legibly a live Agent Session's state reaches the overlay in the first place. Grounded in the real pipeline (docs/V7_AGENT_INTEGRATIONS_TECHNICAL_SPEC.md, agents/notification.rs, agents/board.rs), read in full for this section.

The analogy, stated once, precisely

Handy transcribes audio locally, fast, because the model runs on the same machine — Parakeet V3's own claimed "~5x real-time" is a literal compute-speed fact. notchtap's Agent pipeline does something mechanically unrelated: it relays webhook/hook events from a coding runtime's own process, over loopback HTTP, into a registry and a notification queue. Nothing here can be "5x real-time" in the same sense — there's no model, no inference.

The borrow is a FEELING, not a mechanism: watching a fast local model work reads as continuous and responsive, not as a slow drip of separate, disconnected outputs. That's the bar for how an in-progress Agent Session should read on the Board — as snappy as watching a fast local model work — even though the two systems share no plumbing.

Today's pipeline, as it actually runs

Today — one event in, one Notification out, no batching

Every noteworthy Agent Event becomes exactly one Event in the existing Queue (spec §5's table) — there is no coalescing step anywhere in this path. Confirmed by reading agents/notification.rs in full and grepping debounce|batch|coalesce|throttle across src-tauri/src/agents/: nothing matches. A burst of five tool-progress events inside two seconds is five separate opportunities to enter the Slot (most gated off by informational_notifications default false today) — but the Agent Board's own emission is deduplicated: board.rs's publish_if_changed compares states with AgentState::dedup_eq, which excludes clock-derived fields, so a burst that only touches those doesn't push a new Board render even though each event still counts as its own Queue/Slot opportunity.

Proposal A — batch rapid-fire progress into one card, not N

Proposed — a coalescing window, borrowing a real precedent

notchtap already has a "many small things, one summarized count" concept — queue.rs's batch_total/batch_done (plan 033 decision 4), which drives the queue-slider's "3 of 5" readout across an unrelated burst of queued Notifications. The proposal borrows that VOCABULARY, not that code path: a short coalescing window on the registry side, specifically for the same session's own rapid informational/tool-progress events, producing one updated card instead of a burst of separate ones.

Today — five separate opportunities
Codex — ran grept+0.0s
Codex — ran read_filet+0.4s
Codex — ran grept+0.7s
Codex — ran editt+1.1s
Codex — ran read_filet+1.3s
Proposed — one card, count visible
5Codex — 5 tool calls in the last 1.3s: grep, read_file, edit…t+1.3s

What "batching" would mean here, concretely: a per-session accumulation window — illustratively 600ms, re-armed by each new same-session informational/progress event, capped at an outer ceiling (e.g. 2s) so a continuously busy session still updates at a bounded cadence rather than never flushing. The window closes and publishes ONE agent-state update carrying a rolled-up detail (tool count + last N tool names, reusing the existing bounded details cap from spec §3.2) rather than N separate publishes. Terminal, failure, and permission/input events are NEVER batched — spec §5's table already treats those as one-shot, high-priority, and batching would blunt exactly the urgency that table exists to preserve. This is a genuinely new registry-side concept, not a frontend trick — it belongs beside agents/registry.rs's existing transition/dedup logic, not in AgentBoard.tsx.

Proposal B — a live "still working" ticker on the hero card

Proposed — frontend-only, no new wire field

Today a Working hero shows one static summary line until the next real state change. The bounded per-session history array (AgentSessionView.history, board.rs, already on the wire, capped at MAX_TRANSITIONS_PER_SESSION) already carries recent transitions — proposal is a small local cycling label reading through the last 2-3 entries already present, no new Rust field.

frame 1, 0msran grep across src-tauri
frame 2, 900msedited notification.rs
frame 3, 1800msran cargo test — still working

Motion, specifically: a crossfade between frames, 220ms, var(--ease-notchtap) (cubic-bezier(0.22, 1, 0.36, 1) — the house ease, not a new curve), triggered on a fixed 900ms local interval — same "adaptive local tick, no new wire event" shape AgentBoard.tsx's existing useNowTick already uses for elapsed-time labels (fast/slow tick split, plan 149), reused here rather than invented fresh. This is explicitly the "watching something work" feeling from the analogy above — nothing about it claims to be faster delivery, only a livelier RENDERING of data already on the wire.

Proposal C — real sessions can run parallel subagents; the wire can't say so yet

Proposed — a real modeling gap, not a rendering one

agents/model.rs declares subagent: Option<AgentSubagentSummary> — singular. A runtime that fans out to two or three subagents at once has no wire shape to represent more than one "the session's current subagent" fact at a time; the second concurrent subagent simply has nowhere to go today.

Claude Code — subagent: test runner (working) on the wire today
+ subagent: linter (working) — second concurrent subagent not representable

Directionally: a bounded Vec<AgentSubagentSummary> (same small cap discipline as spec §3.2's other bounded lists, e.g. 16 subagents per event) would let the hero read "3 subagents working" honestly instead of only ever naming one — and would let §04's honesty check stay honest, since nothing today claims parallel-subagent visibility. This is the least fleshed-out of the three proposals here; it needs a real capability-contract decision (spec §1's table would need a new row) before it's anything more than a named gap.
