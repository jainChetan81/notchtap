plan 163 · critical, shipped in production

The token that never resolved

--ease-notchtap was declared only inside vendor/shared-ui/design/tokens.css's @theme inline {} block — Tailwind's Vite plugin only expands that for CSS reachable through an @import "tailwindcss"; root, and the overlay's own entry chain never has one. Every one of the overlay's 45 usages across 10 files silently fell back to the browser's default ease curve instead of the intended settle. This reproduces the actual symptom: an unresolved custom property with no fallback makes the whole transition-timing-function invalid, and the UA default takes over.

both animate 320ms, only the curve differs

BEFORE — token unresolved

Falls back to ease: a slow, indecisive start, most of the motion crammed into the middle.

AFTER — plan 163 fix

cubic-bezier(0.22, 1, 0.36, 1): quick, confident start that settles — the "notchtap" house feel.

review-fix · caught by a fresh, zero-context review pass

Regression: the hover-breathe got clobbered

transition is a single non-additive shorthand. When plans 164/165 gave .expanded and .bare:has(.idle-peek) their own transition: width ... declaration, that higher-specificity rule silently replaced the base rule's transform leg too — on any element that was both .expanded and .hovered at once (a real, frequent combination), the hover-breathe scale stopped easing and started snapping. Fixed by re-adding the transform leg, mirroring what .exiting already did correctly.

both are "expanded"; only the CSS shorthand composition differs

BEFORE — width-only shorthand

.expanded's own transition: width 320ms drops the base rule's transform leg entirely.

AFTER — both legs kept

transition: width 320ms ..., transform 160ms ... — the breathe still eases.

plans 156 · 157 review-fix

Content-exit choreography

Plan 157 replaced StatusRailCard's { y: 8, scale: 0.96 } shorthand with a full transform: "translateY(8px) scale(0.96)" string (GPU-only properties, one declaration). That introduced a real bug: Motion's reduced-motion detection only recognizes discrete prop keys (x/y/scale) in its positionalKeys list — a raw transform string was never in that set, so under prefers-reduced-motion: reduce the interrupt-exit kept sliding and scaling anyway. Fixed with an explicit useReducedMotion() branch that drops the transform and keeps only the opacity fade.
