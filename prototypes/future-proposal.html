Design proposal — Settings → Agents, not shipped

The doctor has no waiting room.

notchtap already runs a full, tested setup diagnostic for every Agent Adapter — notchtap-agent doctor (src-tauri/src/agents/providers/doctor.rs, plan 152). It just has nowhere to be seen: it's a terminal command, and the Settings window's Agents section shows something coarser instead. This proposal borrows a UI shape from Handy — a Tauri app that shows exactly this kind of "is my thing actually set up" state for its own local backends — and applies it to data notchtap already computes.

Draft — not for implementation
Reference: github.com/cjpais/Handy Grounded in: AgentsSection.tsx · providers/doctor.rs · agents/board.rs

§ Ref — what Handy actually does

The pattern being borrowed

Handy (handy.computer, source) is a local speech-to-text app built on the same stack shape as notchtap — Tauri, with a React + TypeScript + Tailwind frontend and a Rust backend. The facts below are quoted or paraphrased from its README; none are guessed.

Confirmed — Handy README
  • Models page — Settings shows each speech model (Whisper Small/Medium/Turbo/Large, Parakeet V2/V3/Unified EN 0.6B) as downloaded or available to download; offline installs work by placing the right file in the app-data models directory, which the app auto-discovers.
  • Two recording modes — push-to-talk (hold a shortcut) and toggle (press to start/stop), both configurable.
  • Recording overlay — a visual indicator during capture, can be switched off (e.g. on Linux, to avoid stealing focus), with "Audio Feedback" as an alternative.
  • Debug mode — Cmd+Shift+D (macOS) / Ctrl+Shift+D (Windows/Linux): verbose logging + the app-data path.
Stated philosophy — quoted
"Handy isn't trying to be the best speech-to-text app — it's trying to be the most forkable one."
"One tool, one job. Transcribe what you say and put it into a text box."

Not verified: this page has no screenshot of Handy's actual Models page — a live-browser check was attempted and the shared Playwright session was already stuck from earlier in this project ("Browser is already in use for .../mcp-chrome-for-testing-fa9bcef"). Everything above comes from the README's prose, not a traced layout, and the mock in § 02 below is an original composition for notchtap's own data — not a copy of Handy's actual pixels.

§ 01 — the gap

Three things Handy's Models page gets right that this section doesn't

Handy's own README frames its Models page as answering one question per model: downloaded, or not. notchtap already computes an equivalent, more detailed answer per Agent Adapter — it's just not on this screen.

1

The setup diagnostic exists, and it's CLI-only

providers/doctor.rs (plan 152, 869 lines, 22+ Rust tests per plans/README.md) reads each runtime's real hook config file and reports exactly what Handy's Models page reports for a model — installed or not, and why not — down to the individual hook: "8/10 hooks wired", missing: Notification, StopFailure, or a command that resolves, is "NOT FOUND at that path", or is a bare name resolved "via PATH" vs. "NOT FOUND on PATH" — real phrasing from doctor.rs's render(). None of it reaches the Settings window; it only prints from notchtap-agent doctor in a terminal.

2

The health chip is coarser than what already exists elsewhere in the app

Three states (Available/Partial/Unavailable) collapse "never configured," "configured but the hook command is broken," and "configured, working, just quiet right now" into shapes that mostly read the same. Handy's model rows don't have this problem because "downloaded" is unambiguous — notchtap's adapters have more failure modes worth showing (see § 02).

3

Every card always shows its full raw JSON, whether you need it or not

Handy's stated ethos — "one tool, one job" — reads as a push toward showing the minimum needed by default. Today's four adapter cards each render a scrollable, always-open <pre> block with the complete hook JSON/TOML (AgentsSection.tsx:283), even for a runtime that's disabled and never touched. See the tally below.

4
always-open JSON/snippet blocks, one per adapter card, regardless of enabled state
4×3
interactive controls per card (toggle + copy + test) = 12, before any setting is touched
5
static "Preview" rows at the bottom that never change and mirror no live state
9

§ 02 — proposed

A setup ladder, built from doctor.rs's own data

The Handy-inspired part: instead of one blended health chip, show the thing Handy shows for a model — a status per unit, unambiguous, plus what to do about a failed one. Here the unit is a hook, and every state below is a real AdapterInstall / CommandTarget variant from providers/doctor.rs, not invented ones. Row copy is taken verbatim from doctor::render()'s own strings (doctor.rs:399-467): "N/M hooks wired", "NOT FOUND on PATH", "NOT FOUND at that path", "plugin file not found — this runtime is not wired". The Claude Code row's checkmark-style pop is the only bounce animation on this page — see § 05 for why.

What this needs, honestly: doctor.rs is written pure/impure-split on purpose (its own header comment: file contents in, report out — reads a home directory and a few paths, no network), so it's realistic to call from a Tauri command. It would need one new #[tauri::command] — say get_agent_doctor_report — added to build.rs's allowlist and capabilities/settings.json, per this repo's own deny-by-default rule for settings-only commands (CLAUDE.md, IPC & security section). That's new surface, not a free lunch.

§ 03 — proposed

Push, not poll — and notchtap already has the plumbing

Today's 5-second poll isn't just slow, it's redundant. The overlay's Agent Board already gets adapter health for free, pushed, every time it actually changes — the Settings window is the one surface still asking for it on a timer.

Proposed — event-driven status, live-dot mock
Claude Code — Available · updated the instant the last event landed, not up to 5s late
t+0.0s
Settings window mounts → get_agent_health invoke
t+1.4s
Real hook fires → registry updates → agent-state event emitted app-wide
t+1.4s
Proposed: Settings window already listening → chip updates instantly
t+1.4s
Today: chip stays stale until the next 5s tick
t+5.0s
Today: setInterval fires → get_agent_health invoke → chip catches up, up to 3.6s late

Why this is a small proposal, not a big one: agents/board.rs:34-49 defines AgentStateSnapshot, and it already carries pub adapter_health: Vec<AdapterHealthView> alongside the session list. That snapshot is emitted app-wide via self.app.emit("agent-state", …) (board.rs:376 — not window-scoped emit_to). And settings.rs:1148's own doc comment for get_agent_health says it reads through "the exact same health_to_view conversion the agent-state overlay channel uses, so both surfaces describe one Adapter Health, never two." The Settings window is already permitted to listen — capabilities/settings.json grants core:event:allow-listen generically. Wiring the health chip to that existing event instead of the poll is, credibly, a frontend-only change: no new Rust command, no build.rs edit, no capabilities edit. (The per-hook wiring ladder in § 02 is the part that needs new backend surface — this doesn't.)

§ 04 — proposed

Trim toward "one tool, one job"

Three specific cuts, each tied to a finding in § 01 — not a general "make it minimal" gesture.

Today
Hook JSON/TOML snippet: always open, up to 160px scroll box, on every card.
"Preview" section: 5 static rows, own SettingsGroup, never reflects real state.
Health signal: one 3-state chip — Available/Partial/Unavailable — per card.
Proposed
Snippet collapses behind a "Show setup snippet" disclosure — closed by default once § 02's ladder shows "wired," open by default while a runtime is un-wired (it's the thing you'd act on).
"Preview" section removed — its five states move inline, one line each, next to the wiring ladder row they describe (real state, not a fixture).
Health signal becomes the ladder itself (§ 02) — the chip is redundant once the ladder is visible, so it's dropped, not duplicated.

The pop-bounce (--ease-notchtap-pop, this app's real overshoot token) is used exactly once on this page, on the one adapter that goes from "not fully wired" to "10/10 wired" — matching this repo's own already-decided rule from plan 164, "scope the shell's pop-bounce out of the hover-reveal leg" (plans/README.md): reserve the bounce for a genuine promotion moment, never for routine hover or a 5-second poll tick. Everything else here is a transition, not a keyframe, so an interruption (the ladder re-rendering mid-animation because a real event landed) retargets instead of restarting. prefers-reduced-motion is handled at the top of this file's stylesheet — consistent with src/settings/base.css, which already flattens all transitions/animations for the real Settings window, unlike the overlay's own reduced-motion gap that plan 156 is separately tracking.

§ 06 — roadmap, not committed work

If this direction is picked up

Ordered by what's cheapest to verify first. None of this is scheduled — it's a proposal for the operator to accept, cut, or reorder, the same way plans 153/154 in plans/README.md shipped as decision documents before any code moved.

Now-sized

Swap the 5s poll for the existing agent-state event

§ 03. Frontend-only per the citations above; worth a spike to confirm the payload really does arrive at the Settings webview unmodified before committing to it as a plan.

Next-sized

Expose doctor.rs through one new settings command

§ 02. Needs the build.rs allowlist entry and a capabilities/settings.json addition this repo requires for every new settings command — small, but not zero, surface.

Later-sized

The trim pass — disclosure, drop the Preview section

§ 04. Lowest technical risk, highest chance of an operator disagreeing on specifics (which rows earn a default-open disclosure) — sequence it after the ladder ships so there's real "wired" state to gate the default on.

This entire document is a proposal. Nothing above is shipped.
