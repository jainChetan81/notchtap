Utils & Tooling — notchtap

Where shared helpers should live, when to extract them, and how to keep them lean · draft 1 · 2026-08-16 · branch chore/anti-slop-cleanup

TL;DR
  • src/lib has only 7 files but the app repeats the same small helpers in many places — 35 typeof guards, 3 copies of isNonNegativeInteger, 2 of isDetailArray, and similar ad-hoc validators in every use*State hook.
  • This plan does not add utils for their own sake. It sets one rule: extract when a pure helper exists in 2+ domains or would prevent a copy-paste on the next feature.
  • Result: 4 small new modules (guards, parse, format, error), one tests rule, and one lint rule. No utils folder sprawl. Every export stays named, tested, and tree-shakable.

2 · Rules for new utilities

2.1 When to extract

  • 2+ domains rule: a pure helper used in two domains (e.g., agent + slot) or copied verbatim twice gets extracted. A helper used twice inside one file stays local.
  • Purity rule: only pure, no-I/O, no-React-state helpers go in src/lib. Anything needing hooks, window, or Tauri stays colocated or in src/settings/*.
  • No speculative utils: don't create a file because it "might be useful." Wait for the second use.

2.2 Where it lives

  • src/lib/guards.ts — tiny type guards: isNonNegativeInteger, isNullableString, isString, isNumber, isDetailArray. No domain imports.
  • src/lib/parse.ts — boundary parsers that compose guards (e.g., parseNonNegativeInt, parseNullableString). Re-exports guards it uses.
  • src/lib/format.ts — display formatters (bytes, uptime already exist; add formatDuration if needed). Extends src/settings/byteFormat.ts rather than replacing it — byte helpers stay where settings already imports them, or re-export from lib/format.
  • src/lib/error.ts — describeActionError + ActionError type + isActionError. Single import for all error-to-string.
  • src/lib/* never imports from src/settings/* or src/components/*. Direction is always inward.
  • Rust stays separate: src-tauri/src/util.rs (or src-tauri/src/lib/parse.rs) only if the same Rust helper appears 3×. Don't pre-split.

2.3 How it looks

  • Named exports only. No default exports. No barrel index.ts that re-exports everything — import straight from the file so tree-shaking and grep stay honest.
  • Every export has a 1-line present-tense doc comment or a SAFETY: note if it uses as. No history, no plan numbers.
  • Maps use satisfies Record<Key, Value>, never as Record. Exhaustiveness is checked by the type, not a cast.
  • Guards are (v: unknown) => v is T and handle null explicitly — callers don't add extra null checks around them.
  • Tests live next to the file: src/lib/guards.test.ts, etc. One test file per util file, not a big shared suite.

2.4 What we don't do

  • No src/utils junk drawer. If you can't name the file after its domain (guards, format, error), it doesn't deserve a file.
  • No wrapping a one-liner in a util to "be consistent." typeof x === "string" with a single use stays inline; the lint exception for guards covers narrow, reviewed sites (see §4).
  • No utils that secretly read global state or the Tauri bridge.

4 · Lint & review gates

  • The anti-slop oxlint plugin stays the gate. Guard helpers in src/lib/guards.ts are the allowed place for narrow typeof checks; the no-runtime-typeof rule should permit them there (or those files get a narrow override), everywhere else the rule keeps firing.
  • require-safety-comment-for-type-assertion still applies in utils — every as needs its SAFETY: line. No new exception.
  • no-unknown-parameters prefers named payload types over Record<string, unknown> — new parse helpers must take unknown at the boundary and return a narrowed type, not widen to any.
  • CI stays npx oxlint + npx tsc --noEmit + npx vitest run. No new tool.

5 · Implementation order (small, reversible steps)

  1. Create src/lib/guards.ts + test. Move the three guard bodies verbatim, keep original files re-exporting or importing. Run npx oxlint — typeof errors should drop 35 → ~26 and the 3 duplicated guards disappear.
  2. Point existing call sites at it. Replace inline bodies in useAgentState, useSlotState, useStatusState with imports. Delete the local copies. Verify cargo test / npx vitest run green.
  3. Move describeActionError → src/lib/error.ts. Keep settings/actionStatus.tsx re-exporting it so no consumer changes import paths in this step.
  4. Introduce src/lib/parse.ts only when the next validator is touched. Don't rewrite all 5 validators at once — do it file-by-file when that hook is otherwise being edited.
  5. Rust (U5) after web. Share the provider security module, then look for repeated serde helpers only if a third copy appears.

Each step is one commit, one file + its test, and must keep npx tsc --noEmit and npx vitest run green. If a step doesn't reduce a duplication count, revert it — that util wasn't needed.
